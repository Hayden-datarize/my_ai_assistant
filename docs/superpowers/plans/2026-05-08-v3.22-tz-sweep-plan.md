#### **upgrade boundary policy (P0-2 in-cycle)** — accept-existing-stored-value 전략
- **stored value 정책**: 기존 `User.lastActiveDate`, `Usage.date`, `Answer.date`는 local TZ 기록값 그대로 유지 (read-only 호환). 신규 write/compare만 `getKstDateStr` 적용.
- **실측 risk**: NY 기준 같은 순간에 `oldLocal=2026-04-18`, `kst=2026-04-19`로 갈라짐 → `recordDailyAnswer`에서 `lastActiveDate` 비교 시:
  - 기존 record가 local TZ였고 사용자가 KST 환경에서 1일이 지나지 않은 경우 → "오늘 활동" → idempotent OK (gap=0)
  - 기존 record가 local TZ였고 KST 자정이 지난 경우 → "어제 활동" → gap=1 정상
  - 즉, **off-by-one은 boundary 1회 발생 가능**. mitigation은 (a) 기존 record가 local TZ로 기록된 사용자의 첫 KST write 시 streak 1 reset 1회만 (allowed), (b) freeze는 lazy regen으로 자연 보호, (c) usage.count는 자정 cross 시 자연 reset (사용자 영향 없음)
- **policy 채택**: **accept boundary 1-day flicker on first KST write** — bridge migration 없음, reset/preserve 강제 없음. 신규 사용자(v5 fresh)는 자연 KST.
- **사용자 검증**: T7에서 사용자 내 데이터의 streak 변동 없는지 1회 cross-check. 만약 streak이 깨지면 v3.22.1 hotfix bridge migration 검토.
