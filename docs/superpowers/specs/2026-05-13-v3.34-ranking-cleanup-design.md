## §2. Architecture

### 2.1 신규 helper — `src/utils/ranking.ts`

| Export | Signature | 책임 |
|---|---|---|
| `scoreEntry` | `(fields: Array<{ text: string; weight: number }>, tokens: string[]) => number` | 토큰별 max(field weight where token hits). 초성-only 토큰은 syllable 매핑 후 binary 평가, substring 토큰은 normalized text contains 평가 |

알고리즘:

```text
score = Σ_token max(weight | token hits field)

- token이 모든 field에 hit 안 하면 → 0 기여 (AND filter 통과 entry는 도달 불가)
- field 여러 곳에 hit해도 max(weight) 한 번만 인정 (occurrence cap=1, binary)
- 같은 토큰을 entry에 여러 번 언급해도 추가 점수 없음 — emphasis ≠ 관련도
```

**토큰 dedup 정책 (Codex 사전 P2-2 흡수)**: `tokens` 배열에 중복 토큰(예: `['react', 'react']`)이 있어도 `scoreEntry`는 **raw token occurrence 기준으로 가산**한다 (dedupe 안 함). 정당 근거: ① 프로덕션 진입점인 `tokenizeQuery`는 whitespace split 결과를 그대로 반환하므로 사용자가 명시적으로 "react react"를 입력했다면 의도 보존, ② AND filter 측면에선 중복 토큰이 결과를 더 좁히지 않아 추가 행동 없음, ③ score는 raw 가산이라 같은 토큰을 두 번 친 사용자는 2배 가중을 받음 (UX 일관). 단위 spec에 raw 가산 invariant 케이스 1건 추가.

정규화·초성 매칭은 `fuzzy.ts`의 `matchesAllTokens`와 동일 정책 (NFC → lowercase / `getInitialConsonants` 재사용). `ranking.ts`는 `fuzzy.ts`에서 helper를 import.

### 2.2 Field weight 정책

| Entity | Field | Weight |
|---|---|---|
| Answer | `questionText` | 2 |
| Answer | `text` | 1 |
| Insight | `text` | 1 (단일 field) |
| Briefing | `title` | 2 |
| Briefing | `summary` | 1 |

- 2:1 비율은 휴리스틱 (실측 분포 미보유 — 할루시네이션 가능성). title/questionText가 짧고 키워드 응축도 높다는 일반 가정 근거.
- v3.34 retro에서 사용자 피드백 기반 tune 가능 (1 constant 조정). retro carry 명시.

### 2.3 정렬 정책 (3-tier)

검색 토큰 존재 여부에 따라:

| 상황 | 정렬 키 |
|---|---|
| `currentTokens.length > 0` | pinned desc → score desc → createdAt(또는 date) desc |
| `currentTokens.length === 0` | pinned desc → createdAt desc (기존 그대로) |

`sortPinThenDesc(items, pinned, sortKey)` helper는 그대로 두고, ranking 적용 spot에서 **score를 sortKey에 인코딩**하거나 별도 `sortPinThenScoreThenDesc` helper를 도입.

선택: **별도 helper** (sortKey 의미 혼선 회피, 단위 테스트 명확).

신규 helper `src/utils/archiveSort.ts`:

```ts
sortPinThenScoreDesc<T>(
  items: T[],
  getPinned: (t: T) => boolean,
  getScore: (t: T) => number,
  getDateKey: (t: T) => string,
): T[]
```

Stable sort (ES2019). `[...items].sort` 패턴 유지.

### 2.4 archive.ts integration — 4 filter spot

| Spot | 현재 | 변경 후 |
|---|---|---|
| scrap entity (line ~703) | `sortPinThenDesc(pool, pinned, b.date)` | 검색 토큰 ≥1 시 `sortPinThenScoreDesc(pool, pinned, getScore, b.date)`. `getScore(b) = scoreEntry([{ text: b.title, weight: 2 }, { text: b.summary, weight: 1 }], tokens)`. 빈 토큰 시 기존 호출 유지 |
| insight entity (line ~719) | `sortPinThenDesc(pool, pinned, i.createdAt)` | 검색 토큰 ≥1 시 `getScore(i) = scoreEntry([{ text: i.text, weight: 1 }], tokens)`. 빈 토큰 시 기존 |
| all merge (line ~761) | `sortPinThenDesc(entries, pinned, sortKey)` | 검색 토큰 ≥1 시 `entry.kind`별로 score 계산 (answer/insight/briefing 각각 weight 정책 적용) → `sortPinThenScoreDesc(entries, pinned, getScore, sortKey)` |
| answer entity (line ~770~) | `filtered.filter(a.text 단독 matchesAllTokens)` + `sortPinThenDesc` | 1) filter 대상을 `${questionText ?? ''} ${text}` 결합으로 확장 2) 검색 토큰 ≥1 시 `getScore(a) = scoreEntry([{ text: a.questionText ?? '', weight: 2 }, { text: a.text, weight: 1 }], tokens)` |

**중요 부수 변경**: spot 4의 filter 대상에 `questionText` 결합 (1.2에서 명시). 이는 기능 확장이며 result-set 관점에선 regression 아님 (questionText hit 항목이 결과에 새로 포함). 다만 **정렬 변화는 의도된 UX**: questionText weight 2 > text weight 1이므로 questionText hit 항목이 기존 text-only hit보다 위로 올라간다. 단위 spec에 "기존 text hit 보존 + 신규 questionText hit 추가 + 정렬 변화 동시 검증" 케이스를 박는다 (Codex 사전 P2-3 흡수).

## §5. Risks / Out-of-scope / Open Questions

### 5.1 Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | Answer filter 대상 확장으로 기존 검색 결과 변동 | 신규 hit는 questionText에 키워드 있는 항목만 추가됨 — 의도된 확장. 기존 hit는 보존. 통합 spec에 명시 케이스 추가 |
| R2 | ranking으로 사용자가 익숙한 createdAt 순서 사라짐 | 검색 토큰 ≥1 일 때만 발동. 빈 검색은 기존 정렬 그대로 — 사용자 멘탈 모델 충격 최소화 |
| R3 | score 동률 발생 시 정렬 안정성 | createdAt desc로 명시적 tie-break. stable sort 보장 (ES2019). 단위 spec에 동률 케이스 명시 |
| R4 | bundle +300 B 초과 (AMBER 진입) | 알고리즘 단순화 (helper LOC < 60), no external deps. T3 직후 1차 측정으로 조기 감지 |
| R5 | Codex CLI external review 환경 | direct CLI 1차 시도 후 실패 시 controller fallback. v3.33 T5 graduated 6단계 정책 적용 |

### 5.3 Open Questions → 사전 결정

| 질문 | 결정 |
|---|---|
| field weight 2:1 vs 1.5:1 vs 3:1? | **2:1** (단순 / 휴리스틱 / retro tune 가능) |
| occurrence cap=1(binary) vs cap=2? | **cap=1 binary** (magic number 0개, 사용자 의도 "더 많은 토큰 hit > 한 토큰 dominance" 정합) |
