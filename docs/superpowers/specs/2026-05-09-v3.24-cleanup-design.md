## §7 Deploy 정책

현재 main HEAD `9a91b9a` 시점에 **v3.22 + v3.23 둘 다 main merge만 된 상태로 Firebase deploy 대기**. v3.24 사이클 시작은 deploy 전에 진입 가능 (origin remote 미등록 — main 직배포 패턴).

### 사이클 끝 deploy 옵션 (T7 retro 직전 사용자 confirm 의무)

| 옵션 | 내용 | 리스크 |
|---|---|---|
| **(a) 묶음 일괄 deploy** | v3.22 + v3.23 + v3.24 한 번에 배포 | production divergence 큼, 사용자 검증 영역 누적 |
| **(b) 단계별 deploy** | v3.22 먼저 → v3.23 별도 → v3.24 별도 (3회) | Firebase deploy 횟수 증가, 단계별 확인 가능 |
| **(c) 2단계** | v3.22 + v3.23 묶음 → v3.24 별도 | 균형, 본 사이클 완료 확정 후 deploy |

**제약 (직배포 패턴 자연 결과)**: 옵션 (b) / (c) 선택 시 **v3.22 / v3.23 deploy는 v3.24 main commit 누적 전 우선 처리해야 한다**. v3.24 commit이 main에 쌓이면 v3.22 / v3.23 단독 deploy 불가 (origin remote 미등록 — main HEAD 시점에 묶여 deploy됨). 따라서 옵션 (b) / (c) 결정은 T0 시점에 사용자 confirm 받고, T1 진입 전 v3.22 / v3.23 deploy 완료. 옵션 (a) 선택 시 T7 retro 직전 묶음 deploy.

옵션 결정은 T0에서, 실제 deploy 시점은 옵션에 따라 T0 (b/c) 또는 T7 (a).
