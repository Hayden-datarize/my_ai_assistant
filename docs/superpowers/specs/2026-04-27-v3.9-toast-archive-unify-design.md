# v3.9 — Undo Toast 시스템 통합 + Archive 카드 통일 (Design)

**Date**: 2026-04-27
**Cycle scope**: D-tight — R1(토스트) + R2(scrap 카드 통일) + v3.8 P2-1/P2-2/P2-6/P2-7
**예상 commits**: 10~12 (spec 1 + plan 1 + T1~T6 6 + 사후 2~3)
**Reviewer 권고**: 표준 리뷰 (10 commits, reversible). 데이터 파괴 동작 없음(P2-2는 이미 v3.8 동작 안에서 atomicity 개선만)

## 1. Why

배포 직후 사용자가 명시 요청한 두 항목 + v3.8 심층 리뷰의 자연 흡수 가능 P2 4건을 한 사이클에 묶는다.

- **R1 — Undo 토스트 unstyled 버그**: v3.8에서 `showUndoToast`가 신설되며 `.dg-toast` / `.dg-toast--undo` 클래스를 도입했는데, 코드베이스 전체에 해당 클래스에 대한 CSS 규칙이 0개다(brainstorm 단계 grep 확인). 사용자가 본 토스트는 사실상 unstyled DOM이었음. 디자인 폴리시가 아니라 스타일 누락이 본질.
- **R2 — Archive scrap 카드 비대칭**: 답변 카드는 `.archive-card` + `data-answer-id` + ✕ 버튼 + delegation click + select 모드 호환. scrap 카드는 같은 베이스 클래스를 쓰지만 `data-answer-id` 없음, ✕ 없음, per-card listener, select 비호환, 추가 `.archive-summary` div. 사용자는 "모두 카드 형식으로 통일" 원함.
- **v3.8 P2-1 (DELETE_UNDO_RESTORED dead key)**: v3.8 메시지 키는 추가됐지만 어떤 사용처도 import 안 함. R1 토스트 시스템 통합 후 자연스럽게 wiring 가능(Undo 클릭 → 복원 성공 토스트).
- **v3.8 P2-2 (atomic Undo 복원)**: 현재 `snapshot.forEach((a) => appendAnswer(a))`가 K건째 throw 시 K-1건만 복원. 단일 write로 atomic 보장 가능.
- **v3.8 P2-6 (storage throw 에러 토스트 검증)**: target/bulk/settings 3 경로 모두 `showToast(getSaveErrorMessage(err))` 호출 자체가 spy로 unverified.
- **v3.8 P2-7 (5초 timeout 통합 검증)**: `toast-undo.spec.ts`는 timer 단위만 검증. delete 흐름의 5초 후 Undo 버튼 사라짐은 통합 검증 누락.

## 4. Goals (성공 기준)

- [ ] Undo 토스트가 명시적 스타일을 가진다(unstyled DOM 0건). 클래스명은 `.toast` 시스템에 통합.
- [ ] Undo 토스트 위치는 **하단 중앙**, 기존 `.toast`(상단 중앙)와 충돌 없음. 두 컨테이너 동시 표시 정상.
- [ ] Undo 클릭 → 복원 → `DELETE_UNDO_RESTORED` 토스트 표시(짧은 일반 토스트). dead key 해소.
- [ ] Undo 복원이 atomic — K건 중 일부 throw 해도 데이터 일관성(rollback or all-or-nothing).
- [ ] scrap 카드도 ✕("스크랩 해제") 버튼 + delegation 패턴 + select 모드 호환.
- [ ] select 모드 진입 시 다른 필터 chip disabled, 모드 종료 시 재활성화.
- [ ] scrap 카드 시각이 답변 카드와 일관(date+title+summary 가독, ⭐ prefix는 유지).
- [ ] storage throw 시 `showToast(getSaveErrorMessage(err))` 호출이 spy로 검증됨(target/bulk/settings 3 경로).
- [ ] delete → 5초 후 Undo 버튼 사라짐이 통합 vitest로 검증됨.

**toast.ts 함수 시그니처 (변경 없음, className + 컨테이너만 교체)**

- `showToast(message, durationMs)` — `el.className = 'toast'`, 컨테이너 `#toastContainer` (top center). 현재 코드는 root에 직접 append라 컨테이너가 없으면 lazy create.
- `showUndoToast(opts)` — `el.className = 'toast toast--undo'`, 컨테이너 `#toastContainer--undo` (bottom center). 동일 lazy create 패턴.

**Fade-out 메커니즘 차이 (의도된 비대칭)**

- 기존 `.toast`: CSS `animation: toastIn 0.3s, toastOut 0.3s ease 2.7s forwards` — 자동 fade. JS는 `setTimeout(remove, durationMs)`만.
- 신설 `.toast--undo`: 5초 동안 표시 + 액션 클릭 즉시 dismiss 가능해서 자동 CSS animation-delay 패턴 사용 불가. `setTimeout` → `el.classList.add('toast-leaving')` → 250ms 후 remove의 explicit 2단계 패턴 유지(v3.8 동작 보존).
- 즉 `.toast-leaving` 클래스는 `.toast--undo`에만 적용. CSS:
  ```css
  .toast--undo.toast-leaving { animation: toastOutDown 0.25s ease forwards; }
  ```

### 5.2 DELETE_UNDO_RESTORED wiring (P2-1)

**Before**:
```ts
onUndo: () => {
  try {
    snapshot.forEach((a) => appendAnswer(a));
    rerenderList();
  } catch {
    showToast(MSG.DELETE_UNDO_FAILED);
  }
},
```

**After**:
```ts
onUndo: () => {
  try {
    saveAnswers([...snapshot, ...loadAnswers()]);  // §5.3 atomic
    rerenderList();
    showToast(MSG.DELETE_UNDO_RESTORED);  // P2-1 wiring
  } catch {
    showToast(MSG.DELETE_UNDO_FAILED);
  }
},
```

- 3 경로 모두 동일 패턴(target/bulk/all reset)

### 5.3 atomic Undo 복원 (P2-2)

- 단일 path: `snapshot.forEach(appendAnswer)` → `saveAnswers([...snapshot, ...loadAnswers()])`
- `appendAnswer`는 `loadAnswers() → push → saveAnswers` 매번 호출(N회 read+write). atomic 단일 write가 효율도 ↑.
- 정렬 보장: `appendAnswer`의 기존 동작은 항상 끝에 push. 단일 write도 동일하게 snapshot을 앞쪽에(또는 뒤쪽에) 일관 위치로 배치.
  - **결정**: snapshot을 앞에 배치(`[...snapshot, ...loadAnswers()]`). 이유: 삭제된 항목이 원래 시간순서대로 복원돼야 하는데, archive는 createdAt 역순 정렬을 rerender 시점에 다시 하니 순서 자체는 무관. 일관성을 위해 snapshot 앞 prepend 채택.
  - 만약 정렬을 createdAt 기반으로 매번 한다면 prepend/append 무관. plan 단계에서 archive sort 확인 후 최종 결정 — **§Open question Q1**.
- 단일 throw → snapshot 전체 미복원 → catch → `DELETE_UNDO_FAILED` 토스트 + 사용자가 다시 시도 가능. 부분 복원의 모호함 제거.

function handleCardClick(e: Event): void {
  if ((e.target as HTMLElement).closest('.archive-card-delete')) return;

    if (briefing) showArchiveDetail({ kind: 'briefing', briefing });
    return;
  }
}

**handleCardDeleteClick 분기 추가**:

```ts
function handleCardDeleteClick(e: Event): void {
  const btn = (e.target as HTMLElement).closest<HTMLButtonElement>('.archive-card-delete');
  if (!btn) return;
  if (selectMode) return;  // P1-1 가드 (v3.8)
  e.stopPropagation();
  const card = btn.closest<HTMLElement>('.archive-card');
  if (!card) return;

  const answerId = card.dataset['answerId'];
  if (answerId) {
    // 기존 답변 삭제 흐름 (변경 없음, §5.2/5.3 atomic Undo 적용)
    return;
  }

  // scrap 해제 흐름 (신설)
  if (card.classList.contains('archive-card--scrap')) {
    const date = card.dataset['briefingDate'];
    if (!date) return;
    const briefings = loadBriefings();
    const idx = briefings.findIndex((b) => b.date === date);
    if (idx < 0) return;
    const wasScrapped = briefings[idx].scrapped;  // 항상 true(scrap 필터에서 보이는 카드)
    try {
      toggleScrap(idx);  // false로 전환
    } catch (err) {
      showToast(getSaveErrorMessage(err));
      return;
    }
    rerenderList();
    showUndoToast({
      message: MSG.SCRAP_UNDO_TOAST,  // 신규 (§5.6 messages)
      actionLabel: MSG.DELETE_UNDO_ACTION,
      onUndo: () => {
        try {
          if (!wasScrapped) return;  // defensive (불가능하지만 invariant)
          const cur = loadBriefings();
          const i = cur.findIndex((b) => b.date === date);
          if (i >= 0 && !cur[i].scrapped) toggleScrap(i);
          rerenderList();
          showToast(MSG.SCRAP_UNDO_RESTORED);
        } catch {
          showToast(MSG.DELETE_UNDO_FAILED);  // 재사용
        }
      },
    });
    return;
  }
}
```

**단건 vs 벌크 atomic 차이 (의도된 비대칭)**

- 단건 ✕: `toggleScrap(idx)` helper 사용 — read-modify-write 1회. 다른 mutator와 race 없음(브라우저 단일 스레드 + 사용자 1번 클릭).
- 벌크: K건 모두 `toggleScrap`을 N번 호출하면 N회 read-modify-write. 첫 호출 후 두 번째 read 사이에 외부 mutation(예: home.ts의 RSS 갱신 큐) 시 race 가능. atomic single write로 해결.

- 사용자에게 모드 정책이 보이도록: 헤더 영역(`#archiveCount` 옆)에 짧은 안내 — `selectMode && currentFilter !== 'all'`이면 "현재 필터 안에서만 선택할 수 있어요"
- "all" 필터 + select 모드: 답변만 보이는 상태(scrap 필터일 때만 scrap 카드 노출). select 자체는 답변 카드만 다룸. 정책 일관.
- scrap 필터 + select 모드: scrap 카드 벌크 해제 가능. **handleBulkDeleteClick에 scrap 분기 추가** — 현재는 답변만 처리. plan 단계 task 분리.

**`handleBulkDeleteClick` scrap 분기**:

```ts
function handleBulkDeleteClick(): void {
  if (selectedIds.size === 0) return;
  if (currentFilter === 'scrap') {
    if (!window.confirm(MSG.SCRAP_BULK_CONFIRM(selectedIds.size))) return;
    const dates = [...selectedIds];
    const snapshot = loadBriefings()
      .map((b, i) => ({ b, i }))
      .filter(({ b }) => b.scrapped && dates.includes(b.date));
    try {
      // atomic: 단일 read-modify-write
      const briefings = loadBriefings();
      for (const date of dates) {
        const i = briefings.findIndex((b) => b.date === date);
        if (i >= 0) briefings[i].scrapped = false;
      }
      saveBriefings(briefings);  // briefings.ts에 export 필요(현재 unexported일 수 있음 — plan 단계 확인)
    } catch (err) {
      showToast(getSaveErrorMessage(err));
      return;
    }
    selectMode = false;
    selectedIds.clear();
    /* 모드 종료 + filter chip 복원 + rerender */
    showUndoToast({
      message: MSG.SCRAP_BULK_UNDO_TOAST(dates.length),
      actionLabel: MSG.DELETE_UNDO_ACTION,
      onUndo: () => { /* snapshot에서 scrapped: true 복원, atomic */ },
    });
    return;
  }
  // 기존 답변 벌크 흐름
}
```

- `selectedIds`가 답변/scrap 모두 다루도록 일반화. 키를 ID(답변) vs date(scrap)로 분기. **§Open question Q3** — Set<string>에 mixed 키 vs 별도 Set 운영.
- `saveBriefings` export 필요 여부 plan 단계 확인.

## 8. Risks & Mitigations

- **R-1** `dg-toast` 클래스명 변경으로 v3.8 신규 테스트(`toast-undo.spec.ts` 등) 회귀 → 클래스 검증을 `.toast.toast--undo`로 한 번에 업데이트, T1 task 안에서 처리
- **R-2** `.toast--undo`와 기존 `.toast` 컨테이너 동시 표시 시 z-index 충돌 → 동일 `--z-toast` 토큰 사용, 위치만 분리(top vs bottom)라 충돌 없음
- **R-3** scrap 카드의 per-card listener 제거가 기존 `dg:archive:filter` 흐름과 충돌 → delegation은 mountArchiveHandlers 시점에 한 번 등록, rerender마다 listener 누적 없음(P2-5 risk 회피)
- **R-4** select 모드 + scrap 필터 + 벌크 해제 시 `toggleScrap`을 N번 호출하면 N번 read-modify-write로 race 위험 → atomic single write로 해결(§5.5)
- **R-5** scrap 카드의 `b.date` unique 가정이 깨지면 같은 date에 여러 briefing 시 ✕가 잘못된 카드를 지움 → Q2 해소 시 다른 키로 교체
