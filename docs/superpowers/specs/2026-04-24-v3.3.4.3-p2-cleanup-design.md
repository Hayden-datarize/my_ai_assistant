## 4. 각 항목 설계 결정

### 4.1 A1 — 라벨 네이밍

**현재**
```
setDefaultInfo(info, total, streak):
  total === 0
    ? '아직 기록이 없어요. 첫 답변을 남겨보세요.'
    : `최근 28일 · ${total}개 달성 · 최장 연속 ${streak}일`
```
(`src/ui/handlers/stats.ts:68`)

**변경**
- `최근 28일` → `이번 주 포함 4주`
- 이유: v3.3.4.2부터 윈도우가 "rolling 28 days"가 아니라 **현재 주 월요일 − 3주 anchor**의 Mon-Sun 4×7 고정 사각형. "28일"은 사실과 무관하게 여전히 맞긴 하지만 시각 의미(4주 사각형)와 어긋남.
- 대안 후보: "최근 4주" / "이번 주 포함 4주" / "지난 4주". **"이번 주 포함 4주"** 채택 — 오늘(현재 주)이 windows 오른쪽 끝에 포함되는 의미를 가장 정확히 표현.
- 주석(`stats.ts:152~156`)의 `DAYS = 28`은 그대로 유지 (구현 상수, 사용자 메시지 아님).

**영향**
- `src/ui/handlers/stats.ts:68` 한 문장 수정
- `tests/unit/heatmap.spec.ts:161,198` 두 assertion 업데이트

### 4.2 A2 — 미래 셀 future-guard

**문제**
오늘이 수요일이면 히트맵 윈도우 마지막 주의 목/금/토/일은 **미래 날짜**인데도 level-0 빈 셀로 렌더되고, 클릭 시 "기록 없음" modal이 열림. 아직 도래하지 않은 날에 "기록 없음"이라고 표기하는 것은 부정확.

**설계**
1. **플래그**: `cell.dataset.future = 'true'` (dataset 기반 상태) + `.is-future` class (CSS hook) + `aria-disabled="true"`.
2. **Native `disabled`는 사용하지 않음**:
   - Button with `disabled`가 일부 브라우저에서 hover 이벤트를 차단 → mouseenter info 업데이트가 깨질 수 있음.
   - 기존 `.btn`/`.btn-primary:disabled` 스타일 의도치 않은 상속 가능.
   - 대신 클릭 핸들러에서 `dataset.future` 가드 early-return.
3. **aria-label**: 기존 `${key}, 기록 없음` → `${key}, 미래 날짜`로 교체.
4. **mouseenter 문구**: `formatCellLabel(key) · 아직 오지 않은 날짜`.
5. **키보드 내비**: `moveFocus`가 미래 셀 **skip**. 끝까지 skip해도 타겟이 없으면 이동 취소 (boundary 유지).
6. **스타일** (`heatmap.css`):
   ```css
   .heatmap-cell.is-future {
     opacity: 0.5;
     cursor: not-allowed;
   }
   .heatmap-cell.is-future:hover,
   .heatmap-cell.is-future:focus-visible {
     transform: none;        /* hover scale 제거 */
   }
   ```

**판정 로직**
```ts
const todayKey = getDateStr(today);
// ISO-8601 date string (YYYY-MM-DD)은 lexicographic sort == chronological sort
const isFuture = key > todayKey;
```
(별도 `Date` 객체 비교보다 간결 + TZ-safe. 기존 `todayKey` 이미 사용 중.)

**거부된 대안**
- **Modal로 "아직 오지 않은 날이에요" 알림**: over-engineering. 접근성상 `aria-label`로 전달하는 것이 더 자연스럽고 KB 사용자에게도 균등.
- **셀 자체 숨기기**: 4×7 Mon-Sun 사각형 모양이 무너짐 (v3.3.4.2 전체 의도 상충).
- **level-0와 시각적으로 동일 유지**: 현재는 "이 날은 비어 있음"과 "이 날은 아직 안 옴"이 구분되지 않음. opacity로 미묘하게 구분해야 인터랙션 전후 일관성 확보.

**오늘이 일요일이면?** 미래 셀 0개 → 아무 변화 없음 (기존 동작 유지).

### 4.3 A3 — Parametric aspect smoke

**현재** (`tests/smoke/cardnews.spec.ts:229~244`)
```ts
test('v3.3.4.3: 5th card height matches row siblings (no double-tall spill)', ...) {
  await page.setViewportSize({ width: 1280, height: 800 });
  ...
  expect(Math.abs(fourth.height - fifth.height)).toBeLessThan(2);
}
```

**변경**
- 기존 단일 테스트 **삭제 후** parametric describe로 대체 (DRY):
  ```ts
  for (const width of [1024, 1280, 1440, 1920]) {
    test(`v3.3.4.3 aspect parity at ${width}px`, ...);
  }
  ```
- 1024 경계 + 1920 최대 쪽은 특별히 중요 (`@media (min-width: 1024px)` 진입과 wide monitor).

**Assertion 기준**
- `≤ 2px` 유지 (기존 기준 그대로).
- 수학적으로 `41/25`는 `gap=16px, track=1040/3≈346.67px` 가정의 근사이므로, 극단 viewport에서 차이가 커질 수 있음 — 만약 1920px에서 허용 2px 초과 시 **A4 cap 적용 후 재검증** (A4가 1920px에서 track을 1200px로 cap하므로 자연스럽게 오차 줄어듦).

### 4.4 A4 — briefing-scroll max-width cap

**문제**
`src/styles/components/cards.css:200~211`

```css
@media (min-width: 1024px) {
  .briefing-scroll { grid-template-columns: repeat(3, 1fr); }
  .briefing-card:nth-child(5) { grid-column: span 2; aspect-ratio: 41/25; }
}
```

- 부모 container 너비 제한 없음 → 1920px+ 초광폭에서 카드 1개가 600px+로 과도하게 넓음 (카드뉴스 전용 가독 비율 이탈).
- v3.3.4.2 리뷰 P2 "briefing-scroll max-width cap (grid-item/margin:auto 충돌 해결 방법 연구)".

**구조 확인** (실조사)
- `.briefing-scroll`의 부모는 `#homeTab > .briefing-scroll` (`home.ts:48`).
- **`#homeTab`은 ≥768px에서 2-column grid** (`home.css:130`): `grid-template-columns: 1fr 1fr`. `.briefing-scroll`은 `grid-column: 1/-1`로 full span되는 **grid item**.
- 즉 메모리의 "grid-item/margin:auto 충돌"이 여기서 발생. Grid item에 `margin-inline: auto + max-width` 조합은 브라우저 구현에 따라 auto margin이 `justify-self: center`로 해석되면서 track 계산이 min-content로 붕괴해 width가 118px로 수축하는 현상 관측 이력.

**설계 — 2단계 시도**

**시도 (a)**: `max-width + margin-inline: auto` (가장 단순)
```css
.briefing-scroll {
  max-width: 1200px;
  margin-inline: auto;
}
```
구현 후 로컬 dev + 1920px 실측. Track 붕괴 현상 없으면 여기서 완료.

**시도 (b) — 백업**: grid item context-aware
```css
@media (min-width: 768px) {
  #homeTab > .briefing-scroll {
    max-width: 1200px;
    width: 100%;
    justify-self: center;
  }
}
```
Grid item에서는 `justify-self: center`가 auto margin의 "가운데 정렬" 의도를 명시적으로 대신. `width: 100%`로 track을 cap 이하로 제한.

**시도 (a), (b) 모두 실패 시 (c)**: 마크업 래퍼 추가. `<div class="briefing-wrap"><div class="briefing-scroll">...`. 마지막 수단 — 마크업 변경 수반.

- **Cap 값**: `1200px` 초안. 데스크톱 1440 / 1920 / 2560 실측 후 조정 가능 (대안: 1280, 1440).
- **기준 viewport**: 1920px → 카드 1개 ≈ (1200−40 padding−32 gap)/3 ≈ 376px. 1024px → ≈ 317px. 1024~1920 사이 자연스러운 증가 + 1920 이후 불변.
- **Padding 주의**: `padding: 0 20px 16px`는 `box-sizing: border-box`(글로벌)라 max-width 내부로 포함. 즉 내용 영역은 `1200 − 40 = 1160px`. 이는 의도된 동작.

**Scroll indicator** (`home.ts:53`의 `#scrollIndicator`)는 `.briefing-scroll` 바깥 sibling이라 영향 없음. `home.css:144`의 `#homeTab > .briefing-scroll`은 full-span grid-column 정의 — **이 정의를 잃지 않도록 cap 스타일을 같은 selector 혹은 하위 media에 추가**.

**대안 및 선택 이유**
- **(a) `.briefing-scroll`에 max-width + margin:auto** ← 초안 채택. 구현 단계에서 grid-item context 충돌(118px 현상) 재현 → 시도 (b) 변형(`justify-self:center + width:100% + max-width`)으로 해결.
- **(b) `#homeTab`에 max-width** → 초안에선 "다른 섹션 영향. 범위 초과"로 기각. **2026-04-24 1920px 실측 후 입장 변경**: briefing만 cap하면 streak banner / question / chat이 full-width로 stretching되어 페이지 좌측이 비대칭으로 비어 보임. 동일한 cap을 `#homeTab` 자체에도 적용(80 + 1200 + 20 = 1300px)하는 게 페이지 일관성에 유리하다고 판단. commit `4023795`로 (a) 위에 (b)를 추가 채택. briefing-scroll local cap은 `#homeTab` cap이 미래에 풀릴 가능성에 대한 defense-in-depth로 유지.
- **(c) 래퍼 `<div class="briefing-wrap">` 추가** → 마크업 수정 필요. 단순 cap을 위한 과도.

**실측 단계** (구현 시 필수)
1. `npm run dev`로 로컬 + browser MCP로 1920×1080 스크린샷
2. Cap 적용 전/후 비교
3. Hayden 확인 후 최종 cap 값 확정 (1200/1280/1440 중)
