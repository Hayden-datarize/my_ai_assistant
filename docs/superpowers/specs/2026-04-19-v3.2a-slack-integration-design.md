# v3.2a — Slack Integration Design

**Date:** 2026-04-19
**Status:** Draft (awaiting user review)
**Scope group:** v3.2a (Slack만; 푸시는 별도 세션)
**Prior art:** `docs/superpowers/specs/2026-04-19-phase-g-wiring-design.md` (v3.1 아키텍처 기준선)

---

## 1. Background & Motivation

v2.0 단일 HTML에는 Slack Incoming Webhook 연동 9개 함수가 작동하고 있었다. Phase D cutover(commit `9e82119`)에서 legacy가 제거되었고, Phase G에서 핵심 기능만 복원했기 때문에 v3.1 현재 `src/services/slack.ts`는 `sendSlack(text)` 스텁만 존재하며 Settings 탭의 슬랙 섹션도 placeholder(테스트 버튼이 토스트만 띄움) 상태다.

v3.2 sub-group 분해에서 v3.2a = 슬랙 + 푸시로 묶여 있었으나, 두 기능의 성격(외부 HTTP vs 브라우저 Notification API)과 테스트 전략이 달라 이번 세션에서는 **슬랙만** 처리한다. 푸시는 별도 세션(v3.2a-2)으로 분리.

## 2. Goals / Non-Goals

### Goals

- 답변 제출 시 Slack 채널에 Block Kit 포맷 메시지 전송 (자동 전송 opt-in + 수동 테스트)
- Settings 탭에서 Webhook URL 저장 / 테스트 / 자동 전송 토글 / 삭제
- legacy v2.0 사용자 데이터(`localStorage.dg_slack`) 자동 호환
- mock 기반 테스트 게이트(vitest + Playwright smoke)로 v3.1 배포 게이트 충족
- CSP에 `hooks.slack.com` 허용 (meta + firebase.json 양쪽)

### Non-Goals (v3.2a 외)

- 주간 리포트 Slack 전송 (`'weekly'` Block Kit type) → v3.2b
- Notion 연동 → v3.2c
- 브라우저 푸시 알림 → 별도 세션
- 양방향 Slack 봇 (백엔드 필요) → Phase 5 W2
- 인사이트 카드/챗 요약 Slack 전송 → v3.2d
- 백엔드 프록시로 Webhook URL 숨김 → Phase 5 W1
- **"수동 재전송" 버튼 (legacy `sendSlackTest` 등가)** — autoSend를 off로 두고 임의로 수동 전송하는 버튼은 이번 세션에서 제외. 근거: 핵심 경로(auto-send + 연결 테스트)만으로 MVP 가치 충분하며, "수동 전송" UX는 홈 탭 답변 영역 근처 버튼 배치가 자연스러운데 이는 v3.2b 리포트 UI 재설계와 함께 검토가 효율적. §4.3의 "테스트" 버튼은 어디까지나 "Webhook URL이 실제로 연결되는지 확인"용 sample payload 전송이며, 실제 오늘 답변을 재전송하는 기능이 아님.

## 3. Architecture

3-layer 분리. 기존 v3.1 컨벤션(`state/user.ts`, `services/gemini.ts` 등)에 부합.

| 파일 | 유형 | 역할 |
|---|---|---|
| `src/state/slack.ts` | **new** | `loadSlackSettings` / `saveSlackSettings` / `clearSlackSettings`. `localStorage.dg_slack` 순수 I/O. 손상된 JSON 방어. |
| `src/services/slack.ts` | **replace** | 기존 `sendSlack(text)` 스텁 제거. 신규: `buildAnswerBlocks(data)` (순수 함수), `sendToSlack(webhook, payload)` (네트워크), `autoSendAnswer(data)` (state 읽고 gating 후 fire-and-forget). |
| `src/ui/tabs/settings.ts` | **extend** | 슬랙 섹션 마크업 확장 + `bindSlackHandlers()` 추가. 이벤트는 이 파일 내부에서 직접 처리 (legacy settings는 CustomEvent dispatch 미사용; §4.2 참조). |
| `src/ui/handlers/home.ts` | **edit** | `submitAnswer()` 내부에 `autoSendAnswer` 호출 1건 추가 (§4.3 타이밍 참조). |
| `index.html` | **edit** | CSP meta `connect-src`에 `https://hooks.slack.com` 추가. |
| `firebase.json` | **edit** | 같은 규칙을 response header CSP에도 추가 (defense in depth). |
| `src/styles/main.css` | **minor edit** | 슬랙 섹션 `<details>` 가이드 스타일 (필요시). |

`src/ui/events.ts`는 **수정 없음**. Slack 관련 이벤트는 settings 탭 내부 로컬 핸들러로 처리하고 document 레벨 dispatch를 쓰지 않는다. `V32_DEFERRED_EVENTS`에 slack stub이 없으므로 제거할 것도 없다.

## 4. Data Model, Payload, Flows

### 4.1 Storage

```ts
// localStorage key: 'dg_slack'
interface SlackSettings {
  webhook: string;      // Slack Incoming Webhook URL
  autoSend: boolean;    // 답변 제출 시 자동 전송 여부
}
```

legacy v2.0 키 그대로. v2.0 사용자는 별도 마이그레이션 없이 기존 설정 유지.

### 4.2 Block Kit Payload ('answer')

legacy `buildSlackBlocks('answer', data)` 포맷 1:1 포팅.

```jsonc
{
  text:  "🌱 Daily Growth — YYYY-MM-DD",   // Slack 알림 fallback
  blocks: [
    { type: 'header',  text: { type: 'plain_text', text: '🌱 Daily Growth — YYYY-MM-DD' } },
    { type: 'section', text: { type: 'mrkdwn', text: '❓ *오늘의 질문*\n<question>' } },
    { type: 'section', text: { type: 'mrkdwn', text: '✍️ *나의 답변*\n<answer 500자 cap>' } },
    // ↓ insight가 있을 때만 포함
    { type: 'divider' },
    { type: 'section', text: { type: 'mrkdwn', text: '💡 *인사이트*\n<insight>' } },
    // ↑
    { type: 'context', elements: [{ type: 'mrkdwn', text: '🔥 연속 N일 · ⭐ N XP' }] },
  ]
}
```

**필드 매핑 (v3.1 schema).**

- `question` ← `submitAnswer()`에서 읽는 `qTextEl?.textContent` (home.ts:403)
- `answer` ← 제출 텍스트 (0–500자 substring; 500자 초과 시 trailing cap)
- `insight` ← `evaluateAnswer`의 반환값 `feedback` 필드 (타입: `{ score: number; feedback: string }`, services/gemini.ts:74). **v2.0의 `insight` 명칭은 v3.1에서 `feedback`으로 변경됨** — Slack Block Kit 라벨은 기존 "💡 인사이트" 유지(사용자 친화 텍스트), 매핑만 `ev.feedback → block.insight` 적용
- `streak` ← `loadUserData().streak` (state/user.ts `User` 인터페이스, `loadUserData` 함수 직접 import)
- `xp` ← `loadUserData().xp` (legacy 스키마는 `totalXp`가 아닌 `xp` 필드; v2.0 Block Kit의 `totalXp` 참조는 명칭 변경됨)
- 날짜 문자열 ← `getDateStr()` (utils/dates; 포맷 `YYYY-MM-DD`)

### 4.3 Flow — Settings 탭

렌더 시점에 `loadSlackSettings()` 결과로 UI 초기화:

- Webhook URL input `value` 채움
- autoSend toggle 상태 반영
- 저장되어 있으면 "자동 전송" 행 + 수동 테스트 행 보이기

**Inputs & buttons:**

1. `#slackWebhookInput` (type="url", placeholder `https://hooks.slack.com/services/...`)
2. `#testSlackBtn` — 현재 입력값으로 `buildAnswerBlocks(sample)` → `sendToSlack` → 결과 UI `#slackTestResult`에 표시. 저장은 하지 않음.
3. `#saveSlackBtn` — URL 형식 검증(`startsWith('https://hooks.slack.com/services/')`) 후 `saveSlackSettings({ webhook, autoSend: 기존값 ?? false })`. 토스트 `✅ Slack Webhook 저장됨`.
4. `#slackAutoToggle` (초기 상태 `autoSend=false`) — 클릭 시 즉시 저장 + 토스트 `✅ 자동 전송 켜짐 / 🔕 자동 전송 꺼짐`.
5. `#clearSlackBtn` — `clearSlackSettings()` + UI 리셋 + 토스트 `🗑️ Slack 연결 해제됨`.
6. `<details>` 접힘 가이드 블록 — "Webhook 만들기 (5단계)" legacy 안내 텍스트 그대로.

### 4.4 Flow — 답변 제출 시 자동 전송

**핵심 결정: insight를 기다릴지 말지.**

v3.1의 `submitAnswer()` (home.ts:395–458) 동작:
- L415: `appendAnswer(answer)` (insight 없이 저장)
- L435–450: 채팅 피드백 생성 (await, 사용자 체감 대기)
- L453–455: `evaluateAnswer(...)` fire-and-forget → `setAnswerEvaluation(id, ev)`

세 시점 중 어디서 `autoSendAnswer`를 호출할지:

| 시점 | insight | 지연 | 결정 |
|---|---|---|---|
| (A) `appendAnswer` 직후 | **없음** | 즉시 | legacy와 가장 유사하나 메시지가 얇음 |
| (B) 채팅 응답 받은 직후 | 없음 | ~1–3초 | 별 이득 없음(insight 여전히 없음) |
| (C) `evaluateAnswer` resolve 콜백 | **있음** | ~2–5초 | 메시지 풍부, Slack은 즉시 볼 필요 낮음 |

**선택: (C)**. 이유:
- Slack 메시지의 핵심 가치 중 하나는 "AI 인사이트"의 동료 공유. insight 없는 전송은 legacy 대비 후퇴.
- 사용자는 답변 제출 후 화면에서 채팅 피드백을 받는 UX 흐름이므로 Slack 채널을 즉시 확인하지 않음 → 수 초 지연 허용.
- 실패 시 Slack 전송이 스킵되어도 답변 저장 자체는 이미 성공. UX 차단 없음.

**구현:**
```ts
// home.ts:453 기존 코드
void evaluateAnswer({ apiKey: key, question: questionText, answer: text })
  .then((ev) => {
    setAnswerEvaluation(id, ev);
    void autoSendAnswer({
      question: questionText,
      answer: text,
      insight: ev.feedback,  // evaluateAnswer 반환 타입: { score, feedback }
    });
  })
  .catch(() => {
    // evaluateAnswer 실패 시에도 Slack 전송은 시도한다 — insight 없이.
    // 답변 제출 자체는 이미 성공했고, insight는 optional 블록이므로
    // 빠진 상태로도 valid Block Kit payload가 생성된다.
    void autoSendAnswer({ question: questionText, answer: text });
  });
```

`autoSendAnswer` 내부:
```ts
async function autoSendAnswer(data: AnswerData): Promise<void> {
  const s = loadSlackSettings();
  if (!s?.webhook || !s.autoSend) return;         // gating
  try {
    await sendToSlack(s.webhook, buildAnswerBlocks(data));
  } catch (e) {
    console.warn('Slack auto-send failed:', e);   // UX 차단 X
  }
}
```

## 5. Error Handling & UX

| 상황 | 동작 |
|---|---|
| `#testSlackBtn` 클릭, 입력 비어 있음 | `#slackTestResult`: `Webhook URL을 입력하세요` (legacy 문구 유지) |
| URL이 `https://hooks.slack.com/services/`로 시작하지 않음 | `#slackTestResult`: `Slack Incoming Webhook URL 형식이 아닙니다` |
| `fetch` 네트워크 실패 (throw) | `#slackTestResult`: `❌ 전송 실패 — 네트워크 오류` |
| 응답 non-200 | `#slackTestResult`: `❌ 전송 실패 — Slack <status>` |
| 테스트 성공 | `#slackTestResult`: `✅ 전송 성공 (<status>)` |
| 저장 시 빈 값 | 토스트 `Webhook URL을 입력하세요`, 저장 진행 안 함 |
| 자동 전송 실패 (답변 제출 흐름) | `console.warn`만, 사용자에게 토스트/에러 노출 안 함 |

## 6. Security / CSP / Secret handling

- `connect-src` 화이트리스트에 `https://hooks.slack.com` 추가 (meta + firebase.json 두 곳). Phase E에서 이미 `connect-src`가 엄격하게 관리되고 있으므로 drift 방지 차원.
- Webhook URL은 사실상 secret(이 URL만 알면 해당 채널에 누구나 post 가능). 현재 방침은 Gemini API 키와 동일 — localStorage 저장, UI input 노출. 이 spec은 **Phase 5 W1의 백엔드 프록시 전까지는 자기 브라우저 저장 방식을 유지**한다.
- UI 하단에 한 줄 안내: `이 Webhook은 이 브라우저에만 저장됩니다`.
- `type="url"` 사용 (Gemini 키는 `type="password"`지만 Webhook URL은 https URL 자체 형태 검증이 중요 → `type="url"`). 마스킹은 하지 않음.

## 7. Test Strategy (mock 기반)

### 7.1 vitest

- `tests/state/slack.spec.ts` — `loadSlackSettings`/`saveSlackSettings`/`clearSlackSettings`
  - 빈 저장소 → `null`
  - 정상 저장 → load 결과 동일
  - 손상된 JSON → `null` (throw 안 함)
  - clear → 이후 load null

- `tests/services/slack.spec.ts`
  - `buildAnswerBlocks` shape:
    - insight 없음 → blocks 4개 (header, section, section, context)
    - insight 있음 → blocks 6개 (header, section, section, divider, section, context)
    - `text` 필드에 날짜 포함
    - answer 600자 입력 → 500자로 cap
    - header `plain_text`, body sections `mrkdwn`
  - `sendToSlack` (mock fetch):
    - URL, `method: 'POST'`, `content-type: application/json`, body가 JSON.parseable
    - non-200 → throw `Error('Slack webhook <status>')`
  - `autoSendAnswer` gating:
    - settings 없음 → fetch 호출 0회
    - `autoSend=false` → fetch 호출 0회
    - webhook만 있고 autoSend=true → fetch 1회
    - fetch failure → swallow (throw 안 함)

### 7.2 Playwright smoke — `tests/smoke/slack.spec.ts` (new)

- Settings 탭 진입 → URL 입력 → 저장 → 페이지 리로드 → 입력값 유지됨 확인

- autoSend toggle on + 답변 제출 (`gemini.evaluateAnswer`도 route intercept로 mock) → `hooks.slack.com` 요청 1회 포착 및 payload 검증

### 7.3 wiring-gap.spec.ts

- 현재 게이트 자동 적용. Slack 관련 이벤트는 events.ts에 없으므로 신규 추가/제거 없음. 테스트는 그린 유지.

## 8. Phase G Risk Mitigation

Phase G lesson: "마크업 이식 ≠ 기능 작동". 이번 작업의 핵심 "기능"은 **Block Kit payload 조립이 Slack API 규격을 만족하는가**이므로, smoke/unit 모두 payload shape 자체를 검증한다(단순 UI 렌더 only smoke는 불충분). §7.1 `buildAnswerBlocks` shape 테스트와 §7.2 Playwright intercepted body 검증이 이 역할을 수행.

Plan discovery lesson: 기존 `src/` 지도화부터. §10 Plan Checklist에 경계면 확정 항목 명시.

## 9. Deployment & Post-Deploy Manual QA

### 9.1 배포 절차

v3.1과 동일: `pnpm build` → `firebase deploy --only hosting`. 사용자 요청 시에만 배포.

### 9.2 배포 직후 사용자 수동 QA (3줄)

Webhook URL 확보 후 아래를 순서대로 확인:

1. Settings → Webhook URL 입력 → **테스트** 버튼 → Slack 채널에 🌱 Daily Growth 메시지 1건 도착.
2. **자동 전송** 토글 ON → 홈에서 답변 1개 제출 → (약 2–5초 후) Slack 채널에 해당 답변 도착(insight 포함).
3. **자동 전송** 토글 OFF → 답변 1개 더 제출 → Slack 채널에 추가 도착 **안 함**.

위 3개 중 하나라도 실패하면 즉시 보고. 롤백 시 한 commit만 revert하면 v3.1 상태로 복귀 가능하도록 단일 feature branch로 구현.

Plan 작성 시 반드시 코드로 확인하고 Plan에 명시해야 할 경계면:

5. Settings 탭 현재 `bindHandlers(container)` 구조 안에 `bindSlackHandlers`를 어떻게 합칠지 (함수 분리 vs 기존 함수 확장).

7. legacy v2.0 `dg_slack` 값이 남아있는 브라우저에서 `loadSlackSettings`가 문제없이 읽는지 (schema 변경 없으니 호환되어야 함 — smoke에 v20-compat 변형 추가 고려).
