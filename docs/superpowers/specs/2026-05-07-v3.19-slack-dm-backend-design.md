## 2. Slack DM Backend

### 2.1 Architecture
```
Frontend (Settings)
  ── 이메일 1회 입력 ──> localStorage `dg_slack: { email, autoSend }`

Frontend (답변 제출)
  ── HTTPS POST { email, question, answer, insight?, streak, xp } ──>
    Firebase Function `sendAnswerDm` (HTTPS, 2세대, region us-central1)
       ├─ ① 도메인 화이트리스트 (`@datarize.ai` 검증)
       ├─ ② rate limit (per-email per-day 10 / per-min 3)
       ├─ ③ Slack `users.lookupByEmail` → user ID
       ├─ ④ Slack `conversations.open` → DM 채널 ID
       └─ ⑤ Slack `chat.postMessage` (blocks payload)
       
  ── 200 OK / 4xx 에러 응답 ──>
Frontend
  ── 성공 시 토스트 / 실패 시 에러 메시지 (rate limit / invalid email / Slack API 오류) ──>
```

**Bot Token**: Firebase Secret Manager (`firebase functions:secrets:set SLACK_BOT_TOKEN`). 코드/git 미노출. 2세대 Functions의 `defineSecret` API 사용.
**maxInstances**: 1 (동시 spike 비용 cap).
**Function source**: `functions/src/sendAnswerDm.ts` 신규 (TypeScript, Firebase Functions 2세대).

### 2.2 Schema Migration
- `dg_slack` localStorage 새 shape:
  ```ts
  interface SlackSettings {
    email: string;       // 변경 (was: webhook)
    autoSend: boolean;   // 동일
  }
  ```
- `loadSlackSettings`: 기존 `webhook` 키만 발견 시 silent reject (null 반환). `email` 키 없으면 무효 → 사용자가 settings에서 재입력.
- `saveSlackSettings(s: SlackSettings)`: 새 shape로 저장.
- `clearSlackSettings`: 동일 (localStorage 삭제).
- 기존 사용자 1명(Hayden)은 Function 배포 직후 settings에서 이메일 1회 입력 필요 (마이그레이션 비용 거의 0).

### 2.3 Frontend UI 변경
- [src/ui/tabs/settings.ts](src/ui/tabs/settings.ts) Slack section 재작성:
  - input 변경: `<input type="url" placeholder="https://hooks.slack.com/...">` → `<input type="email" placeholder="you@datarize.ai">`
  - title 변경: "Slack Webhook" → "Slack 봇 알림"

### 2.4 Backend Function 시그니처
```ts
// functions/src/sendAnswerDm.ts
import { onRequest } from 'firebase-functions/v2/https';
import { defineSecret } from 'firebase-functions/params';

const SLACK_BOT_TOKEN = defineSecret('SLACK_BOT_TOKEN');

interface RequestBody {
  email: string;
  question: string;
  answer: string;
  insight?: string;
  streak: number;
  xp: number;
}

export const sendAnswerDm = onRequest(
  { secrets: [SLACK_BOT_TOKEN], maxInstances: 1, cors: true },
  async (req, res) => {
    // ① POST 메서드, JSON Content-Type 검증
    // ② payload 검증 (Zod 또는 수동): email, question, answer 필수, answer ≤ 500자
    // ③ 도메인 화이트리스트: email.endsWith('@datarize.ai')
    // ④ rate limit (in-memory Map, instance scope, maxInstances=1로 강제)
    //    - per-email last-1min count ≤ 3
    //    - per-email last-24h count ≤ 10
    // ⑤ Slack API 호출 (3단계, 각 fetch 5s timeout):
    //    - users.lookupByEmail
    //    - conversations.open
    //    - chat.postMessage (blocks: buildAnswerBlocks 이식)
    // ⑥ 성공 200 / 실패 분류:
    //    - 400 invalid email (도메인 불일치 or 형식 오류)
    //    - 429 rate limit
    //    - 502 Slack API 실패 (lookup 사용자 없음, postMessage 실패)
    //    - 500 unexpected
  },
);
```

### 2.5 Frontend Service 변경
- [src/services/slack.ts](src/services/slack.ts) `sendToSlack(webhook, payload)` → `sendAnswerDm(data: AnswerData)`:
  ```ts
  export async function sendAnswerDm(data: AnswerData): Promise<void> {
    const s = loadSlackSettings();
    if (!s) throw new Error('Slack 설정 없음');
    const res = await fetch(FUNCTION_URL, {
      method: 'POST',
      body: JSON.stringify({ email: s.email, ...data, streak, xp }),
    });
    if (!res.ok) throw new Error(...);
  }
  ```
- `buildAnswerBlocks` (blocks 구성)은 backend로 이식 (frontend에서는 미사용 → 삭제 또는 backend로 move).
- `autoSendAnswer`: 호출부 동일, 내부 `sendToSlack` → `sendAnswerDm` 교체.

### 2.6 가드 6중
| 가드 | 값 | 적용 위치 |
|---|---|---|
| 답변 길이 cap | 500자 | frontend (현행 ANSWER_CAP) + backend payload 검증 |
| 도메인 화이트리스트 | `@datarize.ai` | frontend HTML5 + backend 검증 |
| per-email 일일 limit | **10회** | backend in-memory rate limit |
| per-email 1분 burst | **3회** | backend in-memory rate limit |
| Function `maxInstances` | **1** | Firebase Functions config |
| Firebase 비용 알람 | **$5/월 도달 시 이메일** | Firebase Console / Cloud Billing budget |

### 2.7 사용자 액션 (배포 전 필수)
1. Slack workspace에 새 App 생성 (https://api.slack.com/apps → Create New App → From scratch)
2. Bot Token 발급 + Scopes:
   - `chat:write`
   - `users:read.email`
   - `im:write`
3. Datarize 워크스페이스에 App install + admin approve
4. Firebase project Blaze 업그레이드 (신용카드 등록, free tier 안에서 비용 0원)
5. Bot Token → Firebase Secret Manager에 저장:
   ```
   firebase functions:secrets:set SLACK_BOT_TOKEN
   ```
6. Firebase Console → Cloud Billing → Budget alert $5/월 설정
7. Function 배포 후 본인 이메일을 settings에 입력 + 테스트 버튼 클릭으로 검증

### 3.3 가설 fix 1 (SW 캐시)
[public/sw.js](public/sw.js)의 stale-while-revalidate 정책 수정:
- rss2json 응답 cache 시 응답 body의 `items[]`에 image 1개 이상 존재 검증 → image 없으면 cache skip (다음 fetch에서 fresh 시도)
- CACHE_NAME bump: `daily-growth-v7` → `daily-growth-v8` (v3.11.1 패턴)
- 이론: 첫 진입에서 image 없는 응답이 캐싱되어 후속 진입에서 stale 그대로 반환되는 경로 차단

### 3.4 가설 fix 2 (RSS first-run race)
[hydrateBriefings](src/ui/handlers/home.ts#L388):
- 빈 list + hasInterests + 미시도 분기에서 `void refreshBriefings()` → `await refreshBriefings()` 직렬화
- render는 await 후로 이동 (skeleton → 실제 카드 paint 한 번에)
- **UX trade-off**: 현행 흐름에서 `refreshBriefings`가 끝에서 `hydrateBriefings()`를 다시 호출하므로(home.ts:619) 직렬화는 paint 횟수를 줄이는 단순화. fetch latency 자체는 동일(5s timeout 그대로). 다만 첫 진입 시 사용자가 보는 "skeleton → 실제 카드 paint" 전환 시점이 뒤로 이동 — race 차단의 trade-off로 인정.

### 3.5 가설 fix 적중 검증 / fallback
- v3.19 retro에 명시적 "production reproduce 시 issue 잔존" 검증 task 포함
- 잔존 시 v3.20 hotfix carry — 진단 정보(tier-reason dataset + console.info)가 fix 근거가 됨

```ts
// tests/helpers/seed.ts (신규)
import type { Page } from '@playwright/test';

export interface PrimeUserOpts {
  gardenIntroduced?: boolean;
  schemaVersion?: 2 | 3 | 4;
  interests?: string[];
}

export async function primeOnboardedUser(page: Page, opts: PrimeUserOpts = {}): Promise<void> {
  const flags = {
    gardenIntroduced: opts.gardenIntroduced ?? true,
    schemaVersion: opts.schemaVersion ?? 2,
    interests: opts.interests ?? ['tech'],
  };
  await page.addInitScript((f) => {
    const user = {
      onboardedAt: '2026-04-01',
      interests: f.interests,
      streak: 0, lastActiveDate: '', xp: 0, earnedBadges: {},
      gamificationMigrated: true,
      gardenIntroduced: f.gardenIntroduced,
      schemaVersion: f.schemaVersion,
    };
    localStorage.setItem('user', JSON.stringify(user));  // production read key
  }, flags);
}
```

## 6. 위험 / 할루시네이션 점검

### 6.1 Slack API
- 사용 API: `users.lookupByEmail`, `conversations.open`, `chat.postMessage` — **확인된 출처** (Slack 공식 docs https://api.slack.com/methods).
- Bot Token scopes: `chat:write`, `users:read.email`, `im:write` — 공식 문서 확인된 출처.
- 다만 Slack API는 변경 가능성 있음, plan 단계에서 docs URL 재확인 권고.

### 6.2 Firebase Functions 2세대
- `onRequest` + `defineSecret` + `maxInstances` API — 공식 docs 패턴이지만 정확한 시그니처는 plan 단계에서 재확인 필요.
- **할루시네이션 가능성 medium** — 1세대(2024 일부 deprecated) vs 2세대 API 혼동 가능. plan 단계에서 https://firebase.google.com/docs/functions/2nd-gen-upgrade 참조 의무.

### 6.3 파란 화면 가설
- 가설 fix 1 (SW image 검증 캐싱) + 가설 fix 2 (await race) 모두 **production reproduce 없는 추정 기반**.
- 가설 빗나갈 가능성 medium. 진단 정보(§3.2)가 동행하므로 v3.20 fix 가능성 보장.
- v3.19 retro에 production 검증 결과 기록 의무.

### 6.4 Backend 도입 zero-cost 정책 변경
- Firebase Blaze 종량제 업그레이드 필수 (free tier 안에서 비용 0원 운영 가능, 다만 신용카드 등록).
- 사용자 확인됨 (Q2 합의).

### 6.5 Rate limit storage 선택
- in-memory Map (instance scope, maxInstances=1로 강제) 권장: 단순, 비용 0
- Firestore: 영속성, 다만 instance 재시작 시 카운트 reset 회피 가능. 추가 비용·복잡도.
- plan 단계에서 결정 (in-memory 우선 권고).
- **사전 review P2-1 확인 사항**: in-memory limit은 instance lifetime 동안만 enforce됨. Cloud Functions 2세대 idle scale-to-zero 정책에서 cold start 시 Map 재초기화 → daily 10회 카운트 reset 가능. 비용 cap은 maxInstances=1 + Firebase budget alert($5)로 상위 enforce. 정확한 daily limit이 필요하면 v3.20에서 Firestore 마이그레이션 carry-forward.

### 6.6 Per-task review 분량
- backend 추가는 코드 review 영역 확장 (functions/src/ 신규). 사전 review의 P0 적발 ROI 입증 패턴 (v3.18 + v3.18.1)을 backend 코드에도 적용 권고.
