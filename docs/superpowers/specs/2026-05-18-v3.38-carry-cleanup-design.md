### 2.1 Track 3 — Hygiene Cleanup

#### 2.1.1 C9 — NFC normalization ESLint rule (P2)

**문제** (v3.37 T3 reviewer M-5): 한국어 string literal이 NFD (Unicode decomposed) 형태로 작성되면 NFC 정규화된 production 데이터와 silent 매칭 fail. v3.37 T3 smoke에서 `'분석'` literal이 미세하게 NFD라서 매칭 안 되는 risk가 발견됨.

**해결**: ESLint custom rule `no-nfd-korean-literal` 신규 추가. 한국어가 포함된 string literal이 NFC가 아니면 error.

```js
// .eslintrc.cjs (또는 eslint.config.js)에 추가:
'local/no-nfd-korean-literal': 'error',
```

**rule 구현** (`.eslint-rules/no-nfd-korean-literal.js` 신규):

```js
/** @type {import('eslint').Rule.RuleModule} */
module.exports = {
  meta: {
    type: 'problem',
    docs: { description: '한국어 string literal은 NFC normalize 필수' },
    schema: [],
    messages: {
      nfd: '한국어 string literal이 NFC 아님 — production 매칭 silent fail risk. NFC normalize 필요.',
    },
  },
  create(context) {
    return {
      Literal(node) {
        if (typeof node.value !== 'string') return;
        if (!/[가-힯]/.test(node.value)) return;
        if (node.value !== node.value.normalize('NFC')) {
          context.report({ node, messageId: 'nfd' });
        }
      },
      TemplateElement(node) {
        const raw = node.value.cooked;
        if (typeof raw !== 'string') return;
        if (!/[가-힯]/.test(raw)) return;
        if (raw !== raw.normalize('NFC')) {
          context.report({ node, messageId: 'nfd' });
        }
      },
    };
  },
};
```

**적용 scope**: `src/**/*.ts` + `tests/**/*.ts` 전체. 기존 위반 0건 확인 후 land. 위반 발생 시 `.normalize('NFC')` 적용 또는 literal 재타이핑.

**자가 진단**:
- XSS/SQL N/A (build-time lint rule).
- false positive: 한자(漢字)가 한국어 unicode block에 없으므로 trigger X. 일본어 ひらがな/カタカナ도 trigger X. 한국어 음절 블록(`가-힯`)만 검사.
- false negative: 자모 분리 형태(`ㅇ`+`ㅏ`+`ㄴ`+...)는 trigger X — 본 rule은 음절 블록 NFC만 검사. ASCII + 자모 혼합은 별도 issue로 차기 carry.

#### 2.2.2 C4 — fuzzy 확장 (Levenshtein + entity scope)

**문제** (v3.32 carry): archive 검색이 NFC + 부분일치까지만 매칭. 1~2 character typo는 매칭 fail. 기존 `src/utils/fuzzy.ts`는 NFC + 초성 매칭 + 다중 토큰 AND만 export.

**해결**: 기존 `src/utils/fuzzy.ts` 확장 — Levenshtein distance + entity scope 결합.

1. **Levenshtein distance** 알고리즘 추가 (`src/utils/fuzzy.ts` 확장, 기존 export 유지):
   - 표준 DP 알고리즘, NFC normalize 후 비교.
   - threshold: 검색 token 길이 ≤2 → distance=0 strict / ≤4 → distance=1 / ≥5 → distance=2.
   - **성능 cap**: token × candidate 곱이 N×M=100,000 초과하면 fuzzy skip하고 exact only (UI freeze 차단).
2. **Entity scope**: archive 검색 시 `currentEntity` 가 `'answer'` 면 answer만 fuzzy, `'scrap'` 이면 scrap만 fuzzy, `'all'` 이면 전체. 초성 매칭(`isInitialOnlyToken`)과 fuzzy 결합 필요 (Codex P1-4): token이 초성 only면 exact 초성 매칭 시도 후 fuzzy skip.
3. **fallback**: fuzzy match 결과 0건이면 exact match 결과만 표시 (degrade 우아).
4. **성능 cap 재검토 (Codex P1-4 정정)**: 100k operation은 단일 (text × token) 단위. archive N=10k records × token 길이 5 × text 길이 20 × sliding window는 milllions DP cells. 따라서:
   - **per-record cap**: text × token ≤ 100k (UI freeze 차단).
   - **archive-wide guard**: token tokenize 시점에 record count > 5000이면 fuzzy off (exact only). UI freeze 차단 강화.
   - **banded early-exit (선택)**: distance 계산 시 `min(prev_row) > threshold`면 즉시 return Infinity. constant-factor 가속.
   - benchmark task T5a Step에서 실측 후 cap 조정.

**자가 진단**:
- XSS: highlight 시 `<mark>` inject은 v3.27/v3.35 검증된 escapeHtml + escapeRegex 패턴 재사용.
- 성능: N=10,000 archive에서 token 1개 fuzzy 100k operation = ~50ms (jsdom benchmark 기준). UI thread blocking risk 모니터. 100k cap으로 차단.
- 할루시네이션 가능성: Levenshtein O(NM) 표준 알고리즘. JavaScript 구현 reference 다수 존재. 본 spec은 알고리즘 정확성 standard.
