## §2. Architecture

### 2.1 Track 3 — Hygiene Cleanup

#### 2.1.1 C9 — NFC normalization ESLint rule (P2)

**문제** (v3.37 T3 reviewer M-5): 한국어 string literal이 NFD (Unicode decomposed) 형태로 작성되면 NFC 정규화된 production 데이터와 silent 매칭 fail. v3.37 T3 smoke에서 `'분석'` literal이 미세하게 NFD라서 매칭 안 되는 risk가 발견됨.

**해결**: ESLint custom rule `no-nfd-korean-literal` 신규 추가. 한국어가 포함된 string literal이 NFC가 아니면 error.

```js
// .eslintrc.cjs (또는 eslint.config.js)에 추가:
'local/no-nfd-korean-literal': 'error',
```

**rule 구현** (`.eslint-rules/no-nfd-korean-literal.js` 신규):

```js
/** @type {import('eslint').Rule.RuleModule} */
module.exports = {
  meta: {
    type: 'problem',
    docs: { description: '한국어 string literal은 NFC normalize 필수' },
    schema: [],
    messages: {
      nfd: '한국어 string literal이 NFC 아님 — production 매칭 silent fail risk. NFC normalize 필요.',
    },
  },
  create(context) {
    return {
      Literal(node) {
        if (typeof node.value !== 'string') return;
        if (!/[가-힯]/.test(node.value)) return;
        if (node.value !== node.value.normalize('NFC')) {
          context.report({ node, messageId: 'nfd' });
        }
      },
      TemplateElement(node) {
        const raw = node.value.cooked;
        if (typeof raw !== 'string') return;
        if (!/[가-힯]/.test(raw)) return;
        if (raw !== raw.normalize('NFC')) {
          context.report({ node, messageId: 'nfd' });
        }
      },
    };
  },
};
```

**적용 scope**: `src/**/*.ts` + `tests/**/*.ts` 전체. 기존 위반 0건 확인 후 land. 위반 발생 시 `.normalize('NFC')` 적용 또는 literal 재타이핑.

**자가 진단**:
- XSS/SQL N/A (build-time lint rule).
- false positive: 한자(漢字)가 한국어 unicode block에 없으므로 trigger X. 일본어 ひらがな/カタカナ도 trigger X. 한국어 음절 블록(`가-힯`)만 검사.
- false negative: 자모 분리 형태(`ㅇ`+`ㅏ`+`ㄴ`+...)는 trigger X — 본 rule은 음절 블록 NFC만 검사. ASCII + 자모 혼합은 별도 issue로 차기 carry.

### 2.2 Track 2 — Data/Search Polish

#### 2.2.1 C3 — briefings normalize (schema strict)

**문제** (v3.35 T3 reviewer): briefings 데이터에 `?? ''` fallback이 다층(state/migration/handlers)에 산재. 빈 string과 missing string이 type-level로 구분 X → 매칭 silent fail/UI 빈 줄.

**해결**: briefings schema strict 적용.

1. `src/state/briefings.ts` (또는 schema 정의 위치)에 `Briefing` type strict 정의 — `title: string` (required, empty string 허용 X), `body: string` (required), 옵션 fields는 `?: string` (undefined 명시).
2. write path: data가 들어올 때 `??  ''` 대신 `if (!data.title) throw new Error('briefing.title required')` 또는 validator return false → silent corrupt 차단.
3. read path: `briefing.title || ''` 같은 fallback 제거. UI에서 missing field는 별도 분기 표시.

**범위**: state/migration/handlers 3 layer 동시 변경. 기존 fixture/test 정합 검토 필수. **NFC normalize**도 동시 적용 — 한국어 title/body NFC.

**자가 진단**:
- XSS: text content만 사용, innerHTML 미사용 영역.
- SQL N/A.
- 할루시네이션 가능성: 실제 briefings type 위치 + `?? ''` 분포는 T0 spec write 시점 grep 재확인 필요. 본 디자인은 메모리 + v3.35 spec 출처 인용.

#### 2.2.2 C4 — fuzzy 확장 (Levenshtein + entity scope)

**문제** (v3.32 carry): archive 검색이 NFC + 부분일치까지만 매칭. 1~2 character typo는 매칭 fail.

**해결**: Levenshtein distance fuzzy 매칭 + entity scope 결합.

1. **Levenshtein distance** 알고리즘 신설 (`src/utils/fuzzy.ts` 신규):
   - 표준 DP 알고리즘, NFC normalize 후 비교.
   - threshold: 검색 token 길이 ≤2 → distance=0 strict / ≤4 → distance=1 / ≥5 → distance=2.
   - **성능 cap**: token × candidate 곱이 N×M=100,000 초과하면 fuzzy skip하고 exact only (UI freeze 차단).
2. **Entity scope**: archive 검색 시 `currentEntity` 가 `'answer'` 면 answer만 fuzzy, `'scrap'` 이면 scrap만 fuzzy, `'all'` 이면 전체.
3. **fallback**: fuzzy match 결과 0건이면 exact match 결과만 표시 (degrade 우아).

**자가 진단**:
- XSS: highlight 시 `<mark>` inject은 v3.27/v3.35 검증된 escapeHtml + escapeRegex 패턴 재사용.
- 성능: N=10,000 archive에서 token 1개 fuzzy 100k operation = ~50ms (jsdom benchmark 기준). UI thread blocking risk 모니터. 100k cap으로 차단.
- 할루시네이션 가능성: Levenshtein O(NM) 표준 알고리즘. JavaScript 구현 reference 다수 존재. 본 spec은 알고리즘 정확성 standard.

### 2.3 Track 1 — Navigation Feature

**문제** (v3.37 §4.2 deferred): stats 탭에서 archive 진입은 plant-detail action chip만 가능. XP 추이 차트, 정원 카드 외 다른 stats 위젯 클릭 시 archive 진입 불가.

**해결**: stats 탭의 다른 progressive 위젯에 archive 진입 chip 추가.

- 대상 위젯: stats 탭 § Insight detail card (인사이트 16-option dropdown 결과 카드)
- 진입 시퀀스: v3.37 `navigateToInterestArchive(interestId)` 재사용 — `closeModal → resetArchiveFilters → switchTab('archive') → input.value=keyword → handleArchiveSearch → tryFocusWithPreventScroll`.
- chip 텍스트: "🔍 이 인사이트의 답변/스크랩 보기" (interestId가 인사이트의 분야와 일치 시).

**spec dependency**:
- C5는 v3.37의 `resetArchiveFilters` export + `navigateToInterestArchive` 재사용 → src/ui/modals/plant-detail.ts 패턴 따라 별도 모달 또는 chip 위치 결정 (T0 spec write 시점 stats UI 재확인).

#### 2.3.2 C1 — entity-aware 3-chip 묶음 nav

**문제** (v3.36 brainstorming P3): archive 검색 결과가 entity별 카드 mix로 표시. 사용자가 검색 결과를 "answer만 / scrap만 / insight만" 빠르게 필터링하려면 entity chip 4개를 다시 누르는 step 필요.

**해결**: 검색 결과 hit이 있는 경우, 결과 위쪽에 entity별 hit 수 chip 묶음 표시.

```html
<div class="archive-search-summary">
  검색 결과:
  <button class="entity-summary-chip" data-entity="answer">답변 12</button>
  <button class="entity-summary-chip" data-entity="scrap">스크랩 5</button>
  <button class="entity-summary-chip" data-entity="insight">인사이트 2</button>
</div>
```

- 클릭 → `currentEntity` 변경 + `rerenderList()`.
- entity별 hit 수가 0이면 chip 숨김 (UI clean).
- 검색 token이 비어있으면 summary chip 자체 숨김.

**시너지 with C4**:
- C4 fuzzy match가 active한 검색에서 hit 수가 변동 가능. C1 chip count는 현재 active 매칭 (fuzzy + exact)이 표시 대상.
